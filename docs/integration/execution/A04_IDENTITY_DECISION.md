# A04 — Identity canonicalization decision record

Phase A (PHASE_A_ISOLATED_ONLY). This record freezes *how* a staged record is
given a deterministic public identity, *which* native fields constitute that
identity, and *what may never* be used as an identity rule. It is the authority
referenced by `integration-staging/src/examdata_integration/contracts/canonical.py`
and `ids.py`, and it is machine-mirrored by
`integration-staging/contracts/identity-keys.json` (generated by
`integration-staging/tools/a04_generate_schemas.py`).

Nothing here reads the original project, the network or a live database. The
only inputs are the A03 private synthetic fixtures.

## 1. Why a canonical identity at all

Every system (CIE, Edexcel, IELTS, TOEFL) already names its own records, and
those native names must survive the integration untouched. The integration adds
a *second*, project-owned identifier so that the same record keeps one stable
name across providers, revisions and routes — without overwriting or reusing the
native one. The rule is:

> the public id is a pure function of the native identity; the native identity is
> never a function of the public id.

Therefore the mapping is deterministic and reversible in the sense that matters:
the native locator is stored alongside the public id, so any public id can be
traced back to its native record. It is deliberately **not** reversible by
arithmetic — the digest is one-way.

## 2. Canonicalization algorithm

For a record of a given `EntityKind`, with an identity mapping `M` whose keys are
exactly `IDENTITY_KEYS[kind]`:

1. **Key check.** `M` must contain every key in `IDENTITY_KEYS[kind]` and no
   extra key. A missing key raises `KeyError`; an extra key raises `TypeError`.
   This stops a caller from silently hashing a half-specified identity or from
   smuggling a non-identity field into the digest.
2. **Per-key encoding.** Each value is encoded by key class (see §3):
   - *code keys* → `normalize_code` (trim, collapse internal whitespace,
     casefold);
   - *hash keys* → `normalize_hash` (lower-case, strip surrounding whitespace);
   - everything else → `normalize_text` (trim, collapse internal whitespace,
     casefold for text; lists are normalised element-wise; mappings are
     normalised by sorted key).
3. **Absence vs unknown.** `None` (absent) encodes as `\x00`; the `UNKNOWN`
   sentinel (present but explicitly not known) encodes as `\x01`. These are
   distinct: "the source did not state a date" and "the source stated that the
   date is unknown" are different facts and must not collide.
4. **Join.** The encoded values are joined in `IDENTITY_KEYS[kind]` order with a
   unit separator, after a leading kind tag, producing
   `canonical_identity_string`.
5. **Digest.** `sha256` of the UTF-8 canonical string → first `DIGEST_BYTES = 20`
   bytes → lower-case RFC 4648 base32 → 32 characters. 20 bytes (160 bits) keeps
   collisions negligible for the expected corpus while staying short enough to
   read in logs and URLs.
6. **Public id.** `public_id = f"{ID_TYPE_PREFIX[kind]}_{digest}"`, e.g.
   `q_…`, `ans_…`, `course_…`. `is_url_safe_public_id` asserts the
   `[a-z]+_[a-z2-7]{32}` shape so a public id can be placed in a route path.

A content revision is computed the same way over the record's *content* fields
(not its identity), so two reads of the same native record that differ in content
get the same id but a different `content_revision`; this is how "same record, new
content" is represented without minting a new identity.

## 3. Normalisation classes

* **code keys** (`CODE_KEYS`): identifiers/枚举-like fields — `system`, `kind`,
  `qualification`, `native_code`, `specification_version`, `session`, `season`,
  `paper`, `component`, `zone`, `role`, `source`, … Case and surrounding
  whitespace are not meaningful for these, so they are casefolded and trimmed.
* **hash keys** (`HASH_KEYS`): `sha256`, `document_sha256`, `content_sha256`,
  `input_revision` — lower-cased hex, whitespace stripped. No other change: a
  hash is opaque.
* **everything else**: `normalize_text` — trim, collapse runs of whitespace,
  casefold. Lists normalise element-wise; mappings normalise by sorted key so
  key order can never change an identity.

`native_id` itself is *text*, not a code key: `"Q41"` and `"q41"` are the same
question in practice, but the fixture declares the exact native string, and that
exact string is preserved verbatim in the stored native locator. The digest uses
the normalised form; the locator keeps the original.

| `syllabus` | `syl` | system, course_native_code, version |
| `container` | `container` | system, kind, native_identity |
| `question` | `q` | system, container_native_identity, native_id, number_path, parent_native_id |
| `answer` | `ans` | system, question_native_id, source, native_answer_key |
| `region` | `region` | system, document_role, document_sha256, page, bbox, coordinate_system |
| `asset` | `asset` | system, media_type, sha256, storage_mode |
| `tag` | `tag` | scheme, version, code |
| `material` | `mat` | system, kind, native_id, applicability |
| `timetable_event` | `tte` | system, qualification, zone, course_native_code, component, date, session |
| `timetable_window` | `ttw` | system, qualification, zone, original_text, source |
| `coverage` | `cov` | scope_kind, scope_native_identity, denominator_kind |
| `job_status` | `job` | scope, input_revision |

Design notes on the less obvious choices:

* **`question` includes `number_path` and `parent_native_id`** because two
  questions in different papers can share a bare native id (`"1"`), and a
  sub-part is only unique relative to its parent. The hierarchy is part of the
  identity, not an attribute of it.
* **`answer` includes `source`** because the same question can carry answers from
  several sources; they are distinct records, and their disagreement is data
  (a `Conflict`), not a collision.
* **`asset` keys on `sha256`**, so the same bytes stored under two names are one
  asset; `media_type`/`storage_mode` participate so an audio asset and an image
  asset with the same hash are not merged.
* **`region` keys on the document hash + page + bbox + coordinate system**, so a
  crop is identified by *where on which document*, never by a row number.
* **`timetable_event` includes `date` and `session`**, and `date` is frequently
  `UNKNOWN` (never fabricated): an event with an unknown date still has a stable
  identity distinct from a dated event.

## 5. Collision and alias policy

* **Collision** — two *different* native identities hashing to the same public
  id. Handled by `IdentityRegistry.register`: the collision is appended to
  `collision_events` **and** an `IdentityCollisionError` is raised. It is never
  silently overwritten, and it is never "resolved" by picking one. (With a
  160-bit digest this should not occur; the path exists so that if it ever does,
  the run stops loudly.)
* **Alias** — an additional native name for an *already registered* identity
  (e.g. `"SB1"` and `"synthetic/cambridge-1"` for the same IELTS book). Aliases
  are normalised with the same text rule (casefold + trim) and resolved through
  `resolve_alias`, which is case-insensitive. If a normalised alias is already
  bound to a *different* public id, the conflict is appended to `alias_events`
  and `AliasConflictError` is raised — an alias never silently rebinds.
* **Native locator** — every registration stores a `native_locator` (the provider
  and the native fields, verbatim). `native_locator(public_id)` returns it, so
  no native information is lost when the public id is minted.

## 6. What may never be an identity rule

Restated from plan §4.2 so it is unambiguous here:

1. **Similarity is never an identity rule.** Title/semantic/filename similarity
   may propose a *candidate link for a human*, never a merge. This is also listed
   in `quality.FORBIDDEN_BASIS` (`title_similarity`, `filename_similarity`).
2. **A database row number is never an identity.** `row_number` is forbidden
   basis; the `region` kind keys on document geometry instead.
3. **An HTTP 200 / plausible URL is never identity or verification.**
4. **Two unofficial sources agreeing is never verification.**
5. **A hash proves integrity, not alignment** — `hash_implies_alignment` is
   forbidden; audio integrity and audio alignment are separate quality
   dimensions.
6. **Synthetic/fixture content never becomes verified real content** —
   `fixture_implies_real` is forbidden, and `synthetic_fixture` is deliberately
   absent from `AUTHORITATIVE_EVIDENCE`.

## 7. Worked examples from the A03 fixtures

* IELTS book: aliases `["SB1", "synthetic/cambridge-1"]` both resolve to the same
  `container_…` id; `resolve_alias("sb1")` is case-insensitive and equal.
* IELTS `Q3` with children `Q3a`/`Q3b`: the parent carries the
  `ancestor`-matched answer; each child's `number_path` is `["Q3", "<child>"]` and
  its `parent_ref` points at `Q3` — the hierarchy is in the identity.
* IELTS `Q41` is a preserved missing answer slot: no `Answer` record is created,
  `answer_presence = missing`, and a `MISSING_ANSWER_SLOT` gap is recorded. The
  slot is never filled with a placeholder.
* IELTS `Q2` grouped alternatives: one `SINGLE_CHOICE` answer whose
  `alternatives = ["A","C","D"]` and `matching_method = alternative`; the option
  set is the union of the answer and the alternatives.
* CIE paper with an unknown date: the `TimetableEvent.date` is `None` and the
  event validates with an "unknown date" note — the date is never guessed.
* CIE `Q1` parts `1(a)`/`1(b)`: registered as `UNKNOWN`-typed children because the
  source does not declare their type; their type is not invented.
* CIE `Q3` conflict: two candidate values, `verification = conflicting`, no
  `manual_decision` — the conflict is preserved, not resolved by the importer.

These are asserted by `integration-staging/tools/a04_roundtrip_fixtures.py`
(61/61 checks) and re-asserted by
`integration-staging/tests/test_contracts_identity.py`.
