## R01 — High: unsupported `done` status bypasses completion validation

File: `integration-staging/tools/b_ledger_update.py`.

The CLI accepts arbitrary `--status` strings. Dependency, gate, and evidence checks apply to `staged_pass`, while `COMPLETE_STATUSES` includes `done`. Against a private copy, `--task B01 --status done` exited 0 despite B00 being partial and every gate being closed. B01 was saved as done. Dependency evaluation would treat that record as complete.

Required correction: validate statuses against an explicit schema; reject `done` and unknown aliases in this private-preparation tool. Apply completion validation to every status that can satisfy dependencies. Define private-preparation readiness separately from actual guarded-action completion.

## R02 — High: patch fields can override protected invariants

Only `task_id`, `mode`, and `status` are prohibited in the patch. The later `task.update(patch)` can overwrite fields set or validated earlier.

Two private reproductions both exited 0:

1. `--status partial` with `{"original_changes_applied": true}` saved a claim of original changes while every gate remained closed.
2. `--status partial` with `{"dependencies": [], "blocked_by": []}` removed B01's dependency and release blocker.

These probes changed only test copies, not the real ledger. They demonstrate that a malformed or overbroad update can make the recorded state inconsistent; they do not imply that an original merge occurred.

Required correction: whitelist patchable fields; reserve dependency/gate/ownership/effect fields; construct and validate the final candidate record before publishing it. Validate dependency transitions and evidence against that candidate. A refused update must leave the ledger bytes unchanged. Corrections to dependency definitions need a dedicated audited operation rather than a generic patch.
