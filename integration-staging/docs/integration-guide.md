## 2. v1 compatibility

The integration adds v2; it does not replace v1. The compatibility contract is recorded per
route in `docs/integration/execution/A12_ROUTE_COMPATIBILITY_WORKSHEET.json`:

- every route of the 71-route baseline (`docs/integration/ROUTE_INVENTORY_CURRENT.json`)
  has a worksheet row with an allowed status and the merge-time requirement;
- legacy payload shapes, default content types, error semantics and path ordering are
  preserved; the staged adapters call the legacy contracts without monkeypatching original
  files;
- active-owner routes (materials, timetable) stay `deferred_active_owner` until their
  release; nothing in those areas was copied or executed in Phase A.

## 3. v2 reference

The v2 API is `/api/v2` with the `examdata.v2/1` response envelope. The endpoint table is
generated from the staged application factory's OpenAPI document:
`integration-staging/docs/v2-api-reference.md` (regenerated by
`integration-staging/tools/a14_build_artifacts.py`).

Wiring rule (plan B04): the shared `examdata/src/examdata/api/app.py` registers the v2
routes **after** the Phase B release, without removing or shadowing a legacy route. Until
then the factory lives only in the staged package and is exercised in-process.

## 4. Configuration precedence

One resolver, five layers (plan §6.1). A setting is taken from the highest layer that
supplies a non-empty value, and every resolved value records its `source` and `origin`:

1. explicit argument (`resolve_config(explicit=...)`)
2. process environment (`EXAMDATA_*` and the legacy aliases)
3. config file (`config_file=...`, must live inside the project/staging tree)
4. manifest defaults
5. built-in default

Legacy aliases (`IELTS_API_DIR`, `TOEFL_API_DIR`) keep working and emit a deprecation
warning; if an alias and its canonical name disagree, resolution **fails**
(`ConfigConflictError`) instead of silently picking one. A secret is never logged: the
resolver reports `***` for `api_key`.

Example settings (see `examdata_integration/runtime/settings.py` for the full table):

| key | environment | role | default |
| --- | --- | --- | --- |
| `data_dir` | `EXAMDATA_DATA_DIR` | data root | `.data` |
| `ielts_dir` / `toefl_dir` | `EXAMDATA_IELTS_DIR` / `EXAMDATA_TOEFL_DIR` | component data | — |
| `component_manifest` | `EXAMDATA_COMPONENT_MANIFEST` | component manifest | — |
| `catalog_root` | `EXAMDATA_CATALOG_ROOT` | published catalog revisions | — |
| `operations_root` | `EXAMDATA_OPERATIONS_ROOT` | checkpoint observation root | — |
| `network_mode` | `EXAMDATA_NETWORK_MODE` | `offline` by default | `offline` |
| `runner_output_budget` | `EXAMDATA_RUNNER_OUTPUT_BUDGET` | runner stdout cap | 4 MiB |
| `total_response_budget` | `EXAMDATA_TOTAL_RESPONSE_BUDGET` | aggregate response cap | 32 MiB |
| `frontend_port` | `FRONTEND_PORT` | frontend server port | 5188 |
| `frontend_upstream` | `EXAMDATA_URL` | API the frontend proxies to | `http://127.0.0.1:8000` |

Example files: `integration-staging/config/staging-config.example.json` and
`integration-staging/config/staging.env.example` (proposed merge targets
`examdata/config.example.json`, `examdata/.env.example`). Neither contains a secret or a
live path.

## 5. Component installation

Runtime components are declared in a component manifest (`examdata.component-manifest/1`)
and launched only through the controlled runner
(`examdata_integration/runtime/runner.py`):

- the manifest lists `component_id`, `name`, `version`, `source_revision`,
  `code_location`, `runtime`, `entry_point`, `supported_commands`,
  `environment_allowlist`, `data_roots`, `read_write_policy` and `health_probe`;
- `code_location` and `entry_point` resolve relative to the deployment root and are
  refused if they escape it;
- the runner allowlists commands, bounds stdout/stderr and total response size, enforces
  timeouts, terminates the process tree, and classifies failures instead of guessing;
- component discovery works independently of the current working directory (plan B02).

In Phase A the only staged component is the synthetic `fake-cli` fixture, which must never
be packaged. The real components (`ielts-api`, `toefl-api`) were neither executed nor
copied; the release manifest records their observed entry-point hashes and defers packaging
to B02/B09.

## 6. Data layout

Source-owned stores stay source-owned (plan §3.4); the integration does not flatten them
into one table.

| data | owner | integration behaviour |
| --- | --- | --- |
| CIE raw locations/hashes | CIE stores | read through a provider; originals fetched on demand |
| IELTS/TOEFL JSON, audio, PDFs | their data roots (`EXAMDATA_IELTS_DIR`, `EXAMDATA_TOEFL_DIR`) | read-only adapters; local assets retained |
| catalog | integration (`EXAMDATA_CATALOG_ROOT`) | identity mappings, searchable metadata, revision pointers |
| published revisions | integration | immutable `revisions/<dataset_revision>.json` + atomic `current.json` pointer |
| checkpoints / job state | source runners | read-only observation; the integration never rewrites a native checkpoint |
| manual decisions and provenance | source stores | preserved and surfaced, never overwritten |

## 7. Identity and quality

Identity (decision record `docs/integration/execution/A04_IDENTITY_DECISION.md`,
machine mirror `integration-staging/contracts/identity-keys.json`):

- the public id is a pure function of the native identity (`sha256` of a canonical
  identity string → 20 bytes → base32 → `q_…`, `ans_…`, `course_…`); the native id and the
  native locator are preserved as aliases;
- absent (`None`) and explicitly unknown (`UNKNOWN`) are different facts and never collide;
- mutable question text, database row numbers, title similarity and semantic similarity
  are never identity rules; collisions are detected by comparing canonical identities.

Quality (machine mirror `integration-staging/contracts/quality-transitions.json`) is a set
of independent dimensions — content, answer presence, answer verification, assets, audio
integrity, audio alignment, region verification — each with an explicit state. Only
authoritative evidence (`copied_snapshot`, `isolated_real_data`, `full_source_validation`,
`deployed_target_validation`) can raise a state; an HTTP 200, agreement between two
unofficial sources, a similar filename, a row number or a fixture is never verification,
and synthetic content never becomes verified real content.

## 8. Source limitations

- Phase A is offline by construction: the staged harness installs a loopback-only network
  guard, and provider tests use an offline transport that is proven to reject calls.
- All staged results are labelled `synthetic_fixture`, `copied_snapshot` or
  `static_inspection`. Fixture and snapshot tests cannot prove source freshness, real
  performance or live deployment.
- No live database, no upstream crawl, no CIE batch resume, and no original service was
  used; real-data migration and restore remain B08 work behind a separate authorization.
- Kimi-owned materials/timetable integration stays deferred until its release.

rebased; `pytest.ini` is staging-only and is not merged.

## 10. Runnable examples

Python — build and read the staged app (in-process, no socket):

```python
import sys
sys.path.insert(0, r"C:\Users\weo\Desktop\api\integration-staging\src")
from fastapi.testclient import TestClient
from examdata_integration.api.app import create_app

client = TestClient(create_app())
body = client.get("/api/v2/courses").json()
print(body["schema"], len(body["data"]))
```

PowerShell — offline configuration resolution:

```powershell
$env:PYTHONIOENCODING = 'utf-8'
$python = 'C:\Users\weo\Desktop\api\examdata\.venv\Scripts\python.exe'
& $python -c "import sys; sys.path.insert(0, r'C:\Users\weo\Desktop\api\integration-staging\src'); from examdata_integration.runtime import doctor; print(doctor.main(['--json']))"
```

Node — the staged client flag is reversible:

```javascript
import {clientEnabled, setClientEnabled, FLAG_NAME} from './client.mjs';

const store = new Map();
clientEnabled({storage: {getItem: (k) => store.get(k) ?? null, removeItem: (k) => store.delete(k), setItem: (k, v) => store.set(k, v)}});
setClientEnabled(false, {storage: {getItem: (k) => store.get(k) ?? null, removeItem: (k) => store.delete(k), setItem: (k, v) => store.set(k, v)}});
// store now holds FLAG_NAME='off'; removing the marker switches the client back on
```
