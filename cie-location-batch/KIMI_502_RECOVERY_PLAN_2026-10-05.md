# CIE 502 阻塞解决与续作方案

目标：查清统一 API 取件失败的实际原因，修复可修复的本地故障，恢复 Phase B 和 Phase C。对应 Kimi 会话：session_08decdcf-1f0e-4c8c-b664-4c2eebc98d1c。

## 已核实事实与结论边界

checkpoint 停在 0472/2026/Jun/41，2026-10-05 09:43:40 +0800；最后三条错误记录的 HTTP 502 body_head 为空。该会话最新报告与用户提供的状态一致。七次同一目标失败无法推出全上游不可用；502 是本地 API 的错误映射，必须进一步区分解析目录、取件、连接、超时、代理和响应校验环节。不要把未知根因当成已确认事实。

## 执行顺序

1. 先离线检查会话原契约、当前工作树及运行服务的真实进程、代码版本、数据目录和日志。确认统一 API 的 /api/v1/paper 调用链、CIE URL 构造、目录候选选择及请求总尝试数确实为 1。检查现有日志里原卷对应的异常、实际上游状态和请求耗时；检查代理环境仅输出是否设置及脱敏摘要，禁止输出凭证。确认空响应体是否由本地异常处理、反向代理或运行旧版本造成。
2. 如有可复现的本地错误，先做最小修复并用离线模拟验证。为失败日志添加安全的 error_class、失败阶段、upstream_status（有实证才填写）、request_id 和耗时；不能泄漏 token、完整敏感查询或响应内容。保留对外 502 语义，禁止把取件失败改成文件不存在或成功。保留历史错误和原断点，不覆盖旧证据。服务重启仅限确认身份的本任务服务，保护其他任务服务、开发数据库及 browser.html。
3. 用户本次明确要求“写一个解决方案，发给他，让他继续干”，作为一次原卷联网续作授权记录。本地工作完成后由你独占执行 0472/2026/Jun/41 的一次原有统一 API 请求，我方不另外发探针。保持单工作线程和原上游锁；不自动重试、不直连 cie.fraft.cn、不换来源、不换卷、不绕过 HTTP 错误停止规则。
4. 若请求失败：先追加 errors.jsonl，原子更新 checkpoint 并恢复 needs_user_resume=true，然后停止所有联网工作。提交这一次失败的具体根因证据与修复结果；若证据仍无法区分单文件与全局，明确保留为未知。不能把本方案解释成无限重试、跳过原卷或更换探针的授权。
5. 若请求成功：按原契约核验 PDF，再继续 Phase B 的 43+1 卷重验，随后 Phase C 主流程。通过右侧 8792 浏览器逐题、逐区域目视核验，导入后回读一致才清理已验收原件；OCR 检查不能代替目视证据。任何后续规定错误立即落盘停机。
6. 全程保护永久索引和日志，不提交、不推送；如目录计数和会话报告存在差异，重新统计并说明口径。81 ms_only、522 qp_only、verification issues 和 8238/2024/Nov/23 的缺口逐项保留，不能宣称全部完成。

## 后续协议选项（本次不执行）

若原卷再次失败，可向用户提出明确的小范围协议变更：通过同一个统一 API，串行选择至多两份已知曾成功的其他 QP，各请求一次，以区分目标文件问题与更广泛故障。这个方案需要用户明确批准不同探针目标；失败时仍按约定停止。跳过原卷和定时重试同样需要单独明确指示。上游真实故障的修复必须由其维护者处理，本地不能保证恢复。
